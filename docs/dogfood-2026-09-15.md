## Findings

All findings below were found by this pass and fixed in this goal; nothing
is left open except the service-worker note, which is behaviour to know
about rather than a defect introduced here.

### 1. Notifications had no backend at all — Critical (Functional), fixed

- **Where:** `Notifications.svelte` (shipped in the M1 shell) called
  `GET /api/v1/notifications`, `POST /notifications/read-all`,
  `POST /notifications/{id}/read`. No such routes, no table, no writers
  existed; the page could only ever show an error. `docs/requirements.csv`
  M21-05 even recorded "recipient notification pending".
- **Repro:** open `/notifications` signed in → the fetch fails; the inbox
  can never work.
- **Fix:** commit `999fe4c` — migration `0023_notifications` (both
  dialects), a notifications repository, the three session-scoped
  endpoints, and writers for the surfaces that produce notifications
  (reply → topic author, sale → author). M12's own notes said M12 is where
  notifications become real.

### 2. Pricing accepted any caller — Critical (Security), fixed

- **Where:** `set_pricing` / `delete_pricing` in `routes/monetization.rs`
  performed no ownership check; the comment claimed "author ownership
  checked via FK on work_pricing", but that foreign key is on `works(id)` —
  it proves the work exists, not who owns it. Any signed-in account could
  reprice or unprice any work.
- **Repro:** as user B, `POST /api/v1/works/<A's work>/pricing` → `200`.
- **Fix:** commit `4592587` — owner-only, strangers get the
  indistinguishable `404`; regression test `only_the_owner_may_price_a_work`
  in `crates/app/tests/milestone_21.rs`.

### 3. Money ledger wrote a fake "platform" account — High (Functional), fixed

- **Where:** the money-tip path inserted the platform's 15% as an
  `author_earnings_ledger` row with `author_account_id = "platform"`. SQLite
  swallowed it (foreign keys off by default); PostgreSQL refuses it —
  `invalid input syntax for type uuid: "platform"`. Tips 500'd on
  PostgreSQL. Two admin metrics queries also targeted a
  `monetization_earnings` table that exists nowhere (SQLite included).
- **Fix:** commit `4592587` — platform-fee rows carry a NULL account
  (the schema's FK to accounts rules out a synthetic account);
  `total_platform_revenue` and the author count query the real ledger with
  the right predicates.

### 4. Forum category links dead-ended at 404 — High (Functional), fixed

- **Where:** `Community.svelte` linked every category to
  `/community/forums/<id>`, but the router had no such route, no view, and
  `api.ts` had no topic/reply fetchers at all. Topics and replies existed
  only at the API layer; posting through the browser was impossible.
- **Fix:** commit `674f7a2` — router matches for
  `/community/forums/<id>` and `/community/topics/<id>`, `ForumCategory`
  and `ForumTopic` views (start a topic, reply, lock honoured), the five
  missing API fetchers, router tests.

### 5. PostgreSQL dialect drift across migrations and reads — Critical (Functional), fixed

Found by the journey extension while wiring the same paths at the HTTP
layer; the browser pass could not even reach them until these were fixed:

- `0021_admin`: the column `window` is a reserved word in PostgreSQL
  (unquoted in schema and upserts).
- `0022_spec_revision`: FK columns declared `TEXT` against UUID primary
  keys; `search_alerts` referenced a `saved_searches` table that exists in
  no dialect (now `saved_views`); counters decoded as `i64` declared
  `INTEGER` instead of `BIGINT` (the 0009 convention); `enabled` was an
  integer column read as bool.
- `0023_notifications` (written this goal): same uuid correction.
- The monetization PostgreSQL strings bound uuid ids without casts and read
  them back without `::text`; `get_pricing` decoded a BOOLEAN column as
  `i64`.
- `0013_community`: `create_topic` inserted integer `locked` into what the
  dialect needs as boolean; the lock toggle used integer literals.

Fix: commit `4592587`. The full journey now passes on PostgreSQL with
zero failed steps; the whole milestone suite still passes on SQLite.

### 6. Discovery feed rendered raw work UUIDs — Medium (Content/UX), fixed

- **Where:** `GET /discovery` returned only `work_id`; `Discover.svelte`
  rendered exactly that. The declared `DiscoveryItem` interface already had
  `title?/author_handle?` — the backend never sent them.
- **Fix:** commit `fd710a9` — `work_details_for` batch-loads
  title + author handle (both dialects), the feed enriches each item, and
  the page renders `title · by author`. The M11 silent-rule test now bans
  influence fields by name (score/reason/affinity/rank) instead of banning
  every field but `work_id`.
- Follow-up `16f7125`: the separator lost its space in Svelte whitespace
  handling.

### 7. Forum topics showed the author as a raw pseud UUID — Low (Content), fixed

- **Where:** `forum_topics.author_pseud` / `forum_posts.author_pseud` store
  pseud id strings (the reply writer resolves them that way); the new
  views rendered them raw.
- **Fix:** commit `f02ac6a` — the topics, single-topic and replies
  endpoints attach `author_handle` via a batch
  `identity::handles_for_pseud_ids`; the views render the handle.

### 8. No author-side pricing UI — High (Functional), fixed

- **Where:** the buyer-side paywall shipped with M21, but no view ever
  called the pricing writers; an author could not price a work from the
  browser, so the purchase journey was only reachable by curl.
- **Fix:** commit `da75978` — a Pricing section in the work editor
  (model free/purchase, minor units, currency) using the existing
  `setWorkPricing`/`deleteWorkPricing` fetchers, pre-filled from the work's
  current pricing. Verified end to end: set 700 through the UI, the public
  pricing endpoint returned `price_minor: 700`.

### 9. Service worker serves a stale bundle after an upgrade — Low (UX), noted

- **Where:** the app registers a service worker; after replacing the
  server binary with a rebuilt frontend, the old bundle kept serving until
  the SW was unregistered. Not a defect introduced by this goal and not
  fixed here; recorded so operators know a hard refresh (or SW update
  strategy) is part of upgrading.

## What was not tested

- Payment processing: `purchase` is the ledger-level flow (ADR 0004);
  no external payment processor exists to drive.
- Realtime presence UI (SSE stream) beyond connection success — the API
  journey covers presence writes.
- Import/export round-trips in the browser (covered by milestone tests
  and the journey's library section).
- Accessibility beyond keyboard-reachable controls observed while driving;
  no axe-core sweep in this pass.

## Bottom line

Nine findings; eight fixed with tests inside this goal, one (service
worker staleness) documented for operators. After the fixes, the full
golden-path journey passes on live PostgreSQL (67 steps, 0 failed) and the
entire golden-path set passes in a real browser against both SQLite and
PostgreSQL with a clean console.
