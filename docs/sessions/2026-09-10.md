## What was built in this session

### The domain crate gained the two decisions Milestone 3 needed

`crates/domain/src/document.rs` is the restricted editor document (spec §8.3):
a closed schema of paragraphs, headings, lists, blockquotes, scene breaks and
bold/italic/link runs, with the canonical JSON, the sanitized HTML and the plain
text all derived from a *validated* document in one place.

The rule it enforces is refusal, not stripping. An unknown node, an unknown
mark, an unexpected attribute, a `javascript:` link, a heading level outside
1–4, a document deeper than 20 levels, wider than 20 000 nodes or 2 MiB of text
— each is refused with a message naming the path. Stripping would mean the
stored document is not the document the author sent, and it would leave the
dangerous case indistinguishable from the harmless one.

`crates/domain/src/content.rs` holds the contributor roles and the publication
readiness check. The property it exists to hold: **ownership belongs to a
pseud, not an account**, so an account that switches faces does not thereby gain
access to what it wrote as the other.

### The database layer gained works, chapters and the outbox

Migration 0003 (both dialects): `works`, `work_contributors`, `chapters`,
`chapter_revisions`, `publication_events`, `collaboration_invites` and
`outbox_events`. `crates/db/src/content.rs`, `collaboration.rs` and `outbox.rs`
are the repositories.

The shape worth remembering, because it is what makes the acceptance criteria
true rather than merely intended:

* **Every mutating statement carries the caller's expected version in its
  `WHERE` clause.** A stale save affects zero rows and writes *nothing at all* —
  not even a revision — because the transaction is dropped rather than
  committed.
* **Revisions are append-only.** Restoring an older one copies it into a new row
  that records where it came from, so a stored reading position always resolves
  and nothing a reader has seen is rewritten.
* **Publication is one transaction**: the readiness check, the contributor
  check, the state change, the publication event and the outbox rows, or none
  of them. No mail is sent from inside it (spec §8.4); the worker that would
  send it arrives in Milestone 5.
* **An idempotency key makes the whole thing replayable.** A second call with
  the same key returns `AlreadyApplied` and enqueues nothing.

### The pages

`/write` is the writing desk — the acting pseud's works, with anything waiting
on it. `/write/:id` is one work: details, the blockers that would stop a
publication, the publication controls, the chapter list and the contributor
list. `/works/:id` and `/works/:id/chapters/:chapterId` are the reader's pages,
and the same work URL answers a contributor with their draft.

The editor (`ChapterEditor.svelte`, Tiptap) is built around three decisions:

* its schema is the *client half* of the server's closed schema, so a
  disagreement surfaces as a refused save rather than as content that silently
  cannot be stored;
* an autosave that distinguishes **saving / saved / offline / conflict**, keeps
  the text on every failure, and offers a browser-local recovery copy rather
  than applying it;
* a link's scheme is checked before it is applied, because the server would
  refuse the whole save and the author would have no idea which keystroke did
  it.

Also decided: the document, pseud and privacy forms render the server's own
schema while the **write** forms do not — a form that shows a field the server
will refuse is worse than one that does not show it.

## Bugs found by testing and by driving the browser, not by reading

Milestone 3 produced three, all now fixed and pinned:

1. **`bind:value` on the field primitives silently did nothing.** `TextField`,
   `Textarea` and `Select` spread their props onto the native element rather
   than declaring a `$bindable` value. The compiler accepted the binding, the
   runtime dropped it, and every Milestone 3 form submitted empty while looking
   correctly filled in. Found by typing a title into the real page and watching
   the server store `""`. Pinned by `FieldBinding.test.ts`, which drives a real
   component binding rather than a DOM event.
2. **Saving a chapter violated a foreign key.** `chapters.current_revision_id`
   was moved before the revision row was inserted, so the editor's first save
   returned `500`. The insert now precedes the pointer move.
3. **An internal fault logged only its masked message.** `ApiError` was logged
   with `Display`, which returns the client-facing text by design; the cause was
   invisible in a test run. Faults now log with `Debug`.

Earlier the same day: the rate limiter was inert in production; `Restricted` was
not a minor state; the class marker sat inside the limiter; a zero refill rate
panicked; the appearance selector applied but never persisted; the build
identity was frozen; the shell kept claiming a session after a password reset;
a failed sign-out threw.

## Open risks and known gaps

Carried forward, with the Milestone 3 additions marked:

1. **PostgreSQL has never been executed.** Every PostgreSQL statement is
   written but unverified; there is no server on this machine. Migration 0003
   added a second dialect difference that only a real server will confirm: a
   circular foreign key is declared inline on SQLite and added with
   `ALTER TABLE … ADD CONSTRAINT` on PostgreSQL, because PostgreSQL validates
   the target when the constraint is created. **This is the largest open risk
   in the project.**
2. **Nothing consumes the outbox.** Milestone 3 writes six kinds of outbox row
   in the transactions that cause them and asserts them in tests, but no worker
   exists, so no notification has ever been delivered and no index updated.
   Milestone 5.
3. **No page has automated browser coverage.** Both frontend defects found in
   Milestone 3 were invisible to the unit tests. The Playwright suite spec §23
   asks for does not exist.
4. **No email transport.** A password reset returns its token outside
   production and logs only the request inside it. Honest, but not shipped.
5. **No common-password list.** Password strength is length plus the rate
   limiter, and this is stated rather than dressed up.
6. **"Withdrawn or newly restricted content disappears from public indexes and
   caches" is only half true.** The de-indexing events are enqueued and tested;
   nothing consumes them yet.
7. **Chapter deletion and reordering have no interface.** Both routes exist,
   are tested through the repository, and cannot be reached from a page; there
   is no undo.
8. **Blocks and mutes are still tables with no behaviour** (M2-06).
9. **Template type-checking is not part of the gate.** `svelte-check` cannot
   start in this checkout for any component, including ones predating the
   session. The Vite build and Vitest are what protect the frontend.
10. **`lorehaven migrate | head` panics on a broken pipe.** Cosmetic; fixing it
    needs `unsafe` for `SIGPIPE`, and the workspace forbids that.
11. **Milestone 1 is incomplete against its own list**: no combobox, the richer
    work-card variants are missing, and layout at 320 px and at 200 % zoom has
    never been measured.
12. **The editor is pinned to Tiptap 2 while Tiptap 3 is current.** The
    installed major is v2 on purpose — the package set was chosen and verified
    as a whole — but `npm view @tiptap/core version` reports 3.x, so this is a
    deliberate lag rather than an accident. Moving up is a frontend-only change
    with `ChapterEditor.svelte`, `autosave.ts` and the schema tests as its
    blast radius, and it is cheaper now than after Milestone 11 adds comment
    editing on the same engine.
13. **Milestone 4 is uncommitted and half-finished** (see the section below).
    Anyone who starts work from this tree inherits nine new files, a migration
    that applies cleanly, and six failing acceptance tests. Anyone who starts
    from `HEAD` inherits none of it and should read
    `docs/plans/milestone-04-reader.md` instead.

`cargo test --workspace` passes for every suite that existed before these files
(app lib 94, milestone_0 11, milestone_2 27, milestone_3 11, db lib 24, domain
lib 49). The new `milestone_4` suite is **3 passed, 6 failed**, and the six
failures group into five causes, none of them yet fixed:

1. **`progress_saved_by_one_device_does_not_overwrite_another`** —
   `no column found for name: revision`. The `ProgressRow` struct derives
   `FromRow` with a field named `revision`, while the column is
   `content_revision`; the query needs `content_revision AS revision` (or the
   field renamed). A mechanical fix.
2. **`the_public_aggregate_is_absent_below_the_minimum_count`** and
   **`the_aggregate_reports_its_count_and_method`** — both build ratings against
   a bare random UUID. `rating.work_id` references `works(id)`, so there is no
   parent row and the insert fails the foreign key. The tests are wrong, not the
   schema: they need a real published work first.
3. **`a_stale_typography_patch_returns_conflict`** — a genuine design gap, not
   a typo. The upsert's `WHERE typography_preference.version = ?` only guards an
   *existing* row; the first write for an account has no row, so the `INSERT`
   branch fires and a deliberately stale `expected_version` is accepted. The
   semantics for "no row yet" need deciding (expected `1`, or create-on-read)
   before this test can pass.
4. **`switching_pseud_shows_a_different_history`** — returned `500` after
   `history_for` gained its `pseud` argument. The per-pseud filter is the right
   behaviour (history belongs to the face that read the work); the failure is in
   the new argument's plumbing and has not been isolated.
5. **`clearing_history_removes_only_the_callers_rows`** — same area; it calls
   `history_for` with the new signature and has not been re-run in isolation
   since.

Two things *were* decided and are worth keeping when this is picked up:

* **History is per pseud, not per account.** `history_for` now takes a `PseudId`
  and filters on it, and `list_history` takes `RequirePseud` rather than
  `RequireSession`. That matches how notes and ratings are already scoped.
* **Position is stored as `position_permille` (INTEGER 0–1000), not a REAL**, so
  the crate's "bind only String and i64" rule holds. The plan suggested either;
  this one was chosen.

Also fixed on the way through, both pre-existing:

* Axum 0.8 rejects `:id` in a route path — the new routes use `{id}`, and two
  paths in `reading.rs` were written the old way and panicked at router build
  time, taking all eleven Milestone 3 tests down with them.
* A `pub use` re-export of `WORDS_PER_MINUTE` in `crates/db/src/reading.rs` that
  nothing used, and a duplicate `decode_rating` signature after a column was
  added.

Nothing in Milestone 4 is reflected in `docs/requirements.csv` or
`docs/verification.md`, deliberately: those two files record what *runs*, and
none of this runs yet.

Work resumed on the same uncommitted tree. Nothing was committed and no

### Fixed, with the run that proves it

The first full suite run after the three edits below was **5 passed, 4 failed**,
down from 3 passed, 6 failed.

1. **`progress_saved_by_one_device_does_not_overwrite_another`** — two column
   mismatches, not one. `ProgressRow` derived `FromRow` with a field named
   `revision` over a column named `content_revision`, and then a field named
   `anchor` over a column named `paragraph_anchor`. Correcting the first only
   moved the error to the second. Both are now aliased — `paragraph_anchor AS
   anchor` on SQLite, and `content_revision::text AS content_revision` plus the
   same alias on PostgreSQL, so rows decode identically on both engines. The
   test passes and both device rows are stored.
2. **`switching_pseud_shows_a_different_history`** — the `500` was a bind-count
   error in `history_for`. Its SQL has three placeholders (`account_id`,
   `pseud_id`, `limit`) and both call sites bound two, so the pseud was never
   sent and `limit` was bound into its position. The missing
   `.bind(pseud.to_string())` was added to both dialect arms. The route now
   answers `200`.
3. **`clearing_history_removes_only_the_callers_rows`** — the test registered
   the handles `"A"` and `"B"`, which the identity rules refuse (three
   characters minimum, 422), so it was asserting about a registration that had
   never happened. Renamed to `AAA` and `BBB`. Passes.

### Applied, not yet re-run

Four further edits were made after that run. `cargo test --workspace` has not
been run since, so these are unverified.

4. **Typography version plumbing.** `GET /settings/typography` returned
   `version: 0` unconditionally, so no client could ever send a current version
   and the conflict test could not construct a genuinely stale one.
   `Typography` in `crates/db/src/reading.rs` gained a `version` field,
   `typography_for` selects it, and the handler returns it instead of the
   literal.
5. **The "no row yet" decision, which the earlier summary left open.** It is
   now decided rather than deferred: when no typography row exists,
   `expected_version` must be `0`; any other value is refused. The guard has to
   be explicit because `ON CONFLICT … DO UPDATE … WHERE` cannot compare against
   a row that does not exist, so the `INSERT` branch fired and accepted a
   deliberately stale version. It is a separate `SELECT version` before the
   upsert.
6. **The two aggregate tests** now create and publish a real work and rate
   that work. `rating.work_id` references `works(id)`, so the bare random UUIDs
   they used could only ever fail the foreign key. This matches what the
   private-rating test already did.
7. **The per-pseud history test** now actually activates the first pseud before
   asserting its list is empty. It previously read `active_pseud` and asserted
   straight away, leaving the *second* pseud active, so the assertion could not
   have passed for the reason it claimed.
