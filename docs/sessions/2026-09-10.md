### What this session actually did

The milestone's backend and pages existed but did not work end to end. Six
defects, none of them found by reading:

1. **`list_reviews` and `upsert_review` were stubs.** A `PUT` to create a review
   reported success and stored nothing; the `GET` returned an empty array
   whatever the database held.
2. **The review route was registered `post(...)` and the frontend sent `PUT`.**
   `405` for every review the interface would ever have sent.
3. **`/library/history` resolved to `history` in the router and `App.svelte` had
   no branch for it**, so the route fell through to `NotFound`.
4. **Three pairs of duplicate pages existed** — `ChapterRead`/`Reader`,
   `WorkRead`/`WorkPage`, `TypographySettings`/`ReaderSettings`. The shell
   rendered the older, emptier one of each pair, so position tracking, ratings,
   notes and typography were in files nothing imported. The duplicates are
   deleted.
5. **`rating_summary` was never constructed** (the compiler said so as dead
   code): the reader had no way to see the public aggregate, because the type
   existed and no route returned it. It is now served on the public work view.
6. **`frontend/src/lib/reading.test.ts` leaked a `localStorage` spy between
   tests**, which is why the suite was green by ordering rather than by passing.

**The next session's first act** is to settle those three with the user: either
close M4-11 with a test and move 12–13 explicitly into M9 and M8, and then tag;
or leave them in M4 and do not tag. Do not tag first and record the gaps after.

### The Milestone 4 browser journey has not been run

The API journeys are pinned by acceptance tests that drive the real router
against a real SQLite file with a cookie jar standing in for a browser, and the
pages compile and pass their unit tests. Nobody has yet opened the site in a
browser and read a chapter. Milestones 2 and 3 each shipped a frontend defect
that only a browser could see (the `bind:value` bug in M3), so this gap should be
closed with the tag, not after it.

## The plan for the rest of the project

`docs/plans/junior-implementation-plan.md` is the document to hand to whoever
builds milestones 5–18. It carries, for each milestone: the journey that defines
it, the migration with its tables and its retention rule, the domain types and
the pure functions that hold the rules, the repository signatures, the routes,
the pages, the acceptance tests **by name**, the pitfalls that have actually
caught people on this codebase, and the definition of done. It is explicit about
where the earlier milestones went wrong, because those are the failures most
likely to repeat:

* a stub that answers `200` and stores nothing is worse than a `501`;
* the router, the shell and the API client are three edits or the screen does not
  exist;
* the same rule in two code paths is one rule and one bug;
* a status written from intent is not a status — every claim of "done" carries a
  command or a test name next to it.
