## Defect 1 — the author was told again on every edit

`PUT /api/v1/works/{id}/reviews` is an upsert, and `6358720` put the
`notifications::notify` call inside the delivered branch of it, so an edit of an
already-public review notified the author a second time. Seen on the running
instance, with the counter taken before and after:

```
review notifications before: 2
edit, still public: Comment posted.
review notifications after edit: 4         <- two rows for one review
```

The notification now waits for a review that was not already public. The
regression test is `milestone_12`'s
`editing_a_public_review_does_not_notify_the_author_again`, which posts a public
review, checks the author has one notification, edits it, checks the author still
has one, and then has a *second* reviewer review the work to prove the guard is
not silencing the feature. Without the guard it fails with the live behaviour
reproduced in a test database — two identical items, one from the post and one
from the edit:

```
assertion `left == right` failed: an edit is not a new review:
{"items":[{"body":"A new public review was posted on Reviewed Once.", ...},
          {"body":"A new public review was posted on Reviewed Once.", ...}], "unread_count":2}
  left: Some(2)
 right: Some(1)
```

The one case the guard misses is written into the comment above it: a review that
was *held* when it was written and delivered by a later edit tells nobody until
the reviewer edits again. Comparing against the stored delivery outcome rather
than `is_public` would close it; it is listed in the handoff as low priority.

## Defect 2 — the panels guard did not guard

`fee36d6` added an `edited` flag to `PrivacySettings.svelte` and
`ContentPreferences.svelte` and consulted it in the effect that re-seeds the
form:

```
if (signature !== seeded && !edited) { draft = { ...values }; seeded = signature; error = null; }
edited = false;
```

Writing a value the effect *reads* re-queues that effect. So the run that skips
the re-seed clears the flag and queues another run, and *that* run seeds — the
edit is discarded one flush later instead of immediately. It reads as a guard and
behaves as a delay.

Proven at component level, not by argument: three tests in
`frontend/src/lib/components/*.test.ts` render each panel, move the control, then
re-render with the changed server copy. Before the fix all three failed —
`expected 'mature' to be 'general'`, i.e. the reader's choice was replaced. The
fix is to stop clearing the flag inside the effect (a save clears it), and the
same tests then pass, including the direction that keeps the panel honest: a copy
arriving *after* a save is still adopted.

## Found while checking the fixes: search does not cover titles

Not part of the overnight round and not a regression — the search shape `768df88`
fixed is unchanged — but it turned up on the instance while the review's probes
were running and it is worth writing down. `rebuild_work_index`
(`crates/db/src/search.rs:34`) takes one `body_text` string and indexes that; the
term table holds chapter prose only, with no title, summary or tags. On the demo
instance:

```
GET /api/v1/public/search?q=cartographer  ->  {"results":[]}        # the work is called The Cartographer's Apprentice
GET /api/v1/public/search?q=quiet         ->  {"results":[{"title":"The Use Case Chronicle", ...}]}
GET /api/v1/public/search?q=salt          ->  {"results":[]}        # ...and "Salt and Signal" exists
```

All seven fixture works have index rows (92–269 terms each), so the index is
populated — the titles simply are not in it. A reader looking for a work by name
is the most ordinary search there is; the handoff carries it as an open item.

## The stale instance, and why a UI probe lied

The first probe of the History link returned `inDom: 0` and looked like proof the
fix did not work. It was not: the process on :8180 had been started at 00:54
*before* the frontend was rebuilt, so the binary it was running embedded the
pre-change bundle. The check that settles it takes two commands —

```
curl -s localhost:8180/ | grep -o 'assets/index-[^"]*\.js'   ->  index-Dr6qyAZp.js
ls frontend/dist/assets/index-*.js                            ->  index-DcLsLbMd.js
```

— and the mismatch is the answer. Two things made this worse than a one-line
confusion: the restart that was supposed to replace the instance had `kill`ed a
stale pid, so the old process still owned the port and the new one exited
silently on a bind error; and `/health/ready` reported `0.1.0+fee36d6`, a build
string that names the *backend* commit and says nothing about which frontend is
inside it. Both are now written down in the handoff's Environment section, along
with the recovery: confirm `ss -ltnp | grep 8180` names the pid you started.

## Test hygiene, and one more reason 16b was red

`16b` was flipped from `test.fail()` to an ordinary test by `c746a6c` and failed
in the first full run of the review (run 12: 29 passed / 1 failed). Two causes,
both in the test:

1. Its preamble emptied the inbox by clicking "Mark all as read" and then
   asserting that button was disabled. The notifications page does not render
   the button at all when the inbox is empty (`Notifications.svelte:96`), and
   test 16 above it leaves the inbox read — so the locator waited for an element
   that could never appear, and the failure was a 60 s timeout on
   `isDisabled()`. The invariant is now "nothing unread", asserted against
   `.notification-list li:not(.read)`.
2. The review body was "A public review nobody was told about." — a sentence the
   positivity gate is entitled to hold, and the default preferences hold
   constructive criticism (`accept_constructive: false`). A test whose subject is
   the notification must first prove the review was *delivered*: the receipt
   ("Comment posted.", the only delivery signal the server sends, spec §12.4) is
   now asserted, and the body is plainly positive.

Worth knowing before debugging this suite: the tests seed each other. Running one
in isolation (`--grep 16b`) fails in `findWork`, because the work a single test
searches for is published by an earlier test in the same file. Run the spec.
